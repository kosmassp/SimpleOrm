# SimpleOrm conformance suite

The executable definition of the library. Every implementation (the C# reference,
the PHP and Go ports, the ports to come) runs the same files; a port is correct when it
passes them unchanged. All formats are JSON so any language can load them.

Layout (populated milestone by milestone):

| Directory | Content | Milestone |
|---|---|---|
| (fixture schema) | there is no schema directory: each implementation builds the fixture database from the fixture entities' metadata (generated `CREATE TABLE`s, no foreign-key constraints) and seeds it from `fixtures/seed.json` before each case (spec/session.md "The step scripts") | 4 (live) |
| `entities/` | expected `EntityMap` JSON for the fixture entities — incl. the Level 3 keys `cascade`, `audit`, `softDelete`, `renamedFrom` and the Level 4 `triggers` block (ADR-0042: `name`, `timing`, `events`, `updateOf`?, `sql` with its tokens unexpanded), present only when declared (regenerate: run tests with `SIMPLEORM_CONFORMANCE_WRITE=1`) | 2 (done) |
| `cases/` | query/error cases: `{ "name", "result", "query", "expect": { "rows" } \| { "error": "MAP-001" } }` — value encoding defined in spec/mapping-rules.md; `result` names a fixture entity, `raw`, or the fixture's base class `BaseModel`, which every implementation resolves only to refuse it (`MAP-028`, ADR-0041; where the language has no subclassing the case is recorded as unreachable and passes by construction — the runner pins the premise, that `BaseModel` is a field-sharing type embedded by value in the fixture entities, and runs no query) | 4 (live) |
| `fixtures/` | seed data (`seed.json`) applied before each case | 4 (live) |
| `migrations-cases/` | runner scenarios: a migration set as data plus `{ "command", "expect": { "applied" } \| { "error" } }` steps (format in spec/migrations.md). ADR-0017/18 additions: top-level `snapshots` (the derived-rollback history), step `renames` (typed pairs the derived rollback inverts) and `expectDefinition` (the MIG-012 view guard), a raw `sql` command (the outside hotfix), `force` on migrate/down, and deep expects `columns` (name-sorted per table) and `ddl` (normalized per view). ADR-0042 additions: step `trigger` (a declaration rendered through the dialect, drop then create; `up` may be absent) and `expectTrigger` (the MIG-012 trigger guard), trigger snapshots (`"kind": "trigger"`), and the deep expect `triggers` (the live trigger parsed back to its declaration, or `null`) | 5 (live) |
| `crud-cases/` | generated CRUD + concurrency scenarios: insert/get/update/delete steps with snapshots (`as`/`from`), `$last` keys, and expected values or error codes | 7 (live) |
| `crud-sql/` | the generated write renderings (ADR-0040 add.3): `{ "name", "entity", "statement": "insert" \| "update" \| "update_only" \| "delete", "properties"? (update_only: property names, the session's order — a hook stamp listed last), "checkVersion"? (delete), "expect": { "sqlite", "sqlserver", "postgres" } }` — each implementation renders the fixture entity's statement through every dialect it ships and compares the exact SQL text (spec/crud.md, spec/dialects.md "Update and delete — the affected-row count"); pure, no database | ADR-0040 add.3 (live) |
| `diff-cases/` | generator diff scenarios (ADR-0017): `{ "current", "snapshot" | null, "renames", "expect": { "isNew", "added", "removed", "renamed", "addedIndexes", "removedIndexes", "unsupported" } }` — both shapes in snapshot form, pure data, no database. With `"kind": "trigger"` (ADR-0042) both sides are trigger declarations (either `null`) and `expect` is `isNew` \| `isChanged` \| `isRemoved` or empty. A current column may carry `"renamedFrom"` — the declared rename of ADR-0038, read like a `renames` entry while it can apply. `addedIndexes` entries are index names that must appear in the emitted create SQL; `unsupported` entries are substrings (usually the column name): messages differ per language, what they name may not; `renames` is a map `{ "old": "new" }`, `renamed` lists `[old, new]` pairs in emitted order, `current.asOfVersion` is `0` | ADR-0017 (live) |
| `amend-cases/` | `diff --amend` scenarios (ADR-0017 add.3): a migrations directory as data — `files` (path + whether it carries the generator's header, a root's dialect stamp) and `snapshots` at their paths — plus the `command` (`amend`, `force`, `name`, `dialect`, `applied`), and `expect`: exit code, files `deleted`/`written`/`kept`, content `contains`/`omits` fragments, `output`/`error` substrings. Against the fixed fixture `amend_widgets` (V0001, V0002, one step each; model id/name/remark) each implementation defines natively; no database (format in `amend-cases/README.md`) | ADR-0017 add.3 (live) |
| `snapshot-cases/` | exact snapshot exports (ADR-0017): `{ "entity", "kind"?, "asOfVersion", "generatedAt", "expect": <the full document> }` — each implementation exports its native fixture entity at the pinned time and must produce the expected document exactly (tables by columns, views by normalized DDL; `"kind": "trigger"` with `"trigger": "<name>"` the declaration the entity links, ADR-0042) | ADR-0017 (live) |
| `trigger-sql/` | the trigger renderings (ADR-0042): `{ "name", "relation", "relationKind": "table" \| "view", "trigger": { "name", "timing", "events", "updateOf"?, "sql" }, "expect": { "sqlite" \| "sqlserver" \| "postgres": { "create": [...], "drop": [...] } \| { "error": "DDL-005" } } }` — a neutral declaration in, the exact create and drop statements per dialect out (spec/dialects.md "Triggers"); every implementation renders every case through every dialect it ships; pure, no database | ADR-0042 (live) |
| `load-cases/` | relationship-loading scenarios (ADR-0021): `{ "load": { "entity", "navigation", "keys" }, "expect": { "loaded": { "<key>": object \| null \| array } } \| { "error": "REL-001" } }` against the seeded fixture database — singular navigations expect an object/null, collections an array ordered by target key (value-wise); a key is an integer or an array of parts in key order (composite keys join with `\|` in `loaded`); listed columns checked, lengths exact (format in spec/loading.md) | L2 M3 (live) |
| `ast/` | criteria query AST as JSON with the exact expected SQL and ordered parameter values per dialect, or an error code (`QRY-006`/`QRY-007`) — rendering is pure, no database. Ops: `eq ne gt ge lt le like in is_null is_not_null and or not`; `select` carries `where` (implicitly ANDed), `orderBy` (`property` + optional `order: "desc"`), `limit`, `offset`; parameters are `@c0…` in render order (WHERE, then limit, then offset); the `expect` block carries `sqlite`, `sqlserver`, and `postgres` entries and every implementation renders every case through every dialect it ships (spec/dialects.md) | L2 M2 (live) |
| `ast/level2/` | the Level 2 extensions of the same format (ADR-0022 add.1, ADR-0029): `projection` (root property names), `joins` (`entity`, `alias`, optional `parent`, `on` pairs `[parent, target]`, `project`), and the `in_select` op whose nested `select` names its own `entity`. Level 0–1 ports enumerate only the top level; a Level 2 port adds this folder | L2 exit (live) |
| `tracking-cases/` | identity map + change tracking step scripts (ADR-0035): `{ "name", "tracking": "tracked" \| "untracked", "steps": [...] }` replayed against the seeded fixture database — steps `get`/`new`/`set`/`insert`/`update`/`updateOnly`/`delete`/`refresh`/`load`/`begin`/`commit`/`rollback` on named instances (`as`/`ref`), expectations `same`/`notSame`/`dirty`/`value`/`tracked`/`sameValue`/`count`, `expectWritten` on an update, or an error code (format in spec/session.md "Tracking") | L3 M1 (live) |
| `flush-cases/` | unit-of-work step scripts (ADR-0036): the tracking vocabulary plus `persist`/`remove`, `flush` with `expectStatements` — the ordered `{ "op", "entity", "columns"? }` list the dialect was asked to render — and `expectSummary`; `new` may carry navigations; a graph in, the exact statement sequence out (format in spec/unit-of-work.md) | L3 M2 (live) |
| `hook-cases/` | the declared hooks (ADR-0037) under the fixed clock `2026-08-29T00:00:00Z`: created-at filled, updated-at stamped on every row-changing write, a soft delete observed as the flag-setting `update` (format in spec/hooks.md) | L3 M3 (live) |
| `merge-cases/` | detach and merge step scripts (ADR-0037): the same vocabulary plus `detach` (`ref`) and `merge` (`ref`, `as`); `CRUD-001`/`CRUD-002`/`UOW-001` (format in spec/unit-of-work.md "Detach and merge") | L3 M3 (live) |

Rules:

- Expected values use a small documented JSON encoding for dates, decimals, GUIDs, and
  byte arrays (documented here when `cases/` lands in milestone 4).
- Error codes are the cross-language contract for failures.
- A feature without a conformance case is not done.
